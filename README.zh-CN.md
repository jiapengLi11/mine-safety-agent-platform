# MineGuard Agent 矿区智能安全监控与处置平台

MineGuard Agent 不是“YOLO 检测加一个聊天窗口”，而是一套把视觉检测结果转化为可追踪业务事件，并通过确定性规则、规程证据、受控 Agent、人工审批和工单闭环完成安全处置的工程化平台。

> 当前阶段：第一阶段开发中。已经完成后端工程骨架、核心领域规则、数据库基线、自动化测试、虚拟机真实部署，以及Agent领域评测与发布门禁底座。Kafka 消费、RTSP 推理、工单、RAG、Agent 和 Vue 控制台仍属于后续开发，不作为已完成功能宣传。

## 一句话说明

平台将“摄像头中的一次模型预测”依次转化为“可校验检测事件、稳定时序告警、有规程依据的风险研判、受权限控制的处置动作、可审计工单以及可回流训练的数据样本”。

## 为什么不能检测到就直接告警

真实视频中会存在模型置信度抖动、抽帧间隔、网络延迟、重复消息、画面遮挡和短时误检。若单帧检测直接触发告警，系统很容易出现告警风暴和证据错位。

MineGuard 第一条规则原型采用“20 秒内至少 3 次吸烟检测”策略，并处理以下工程问题：

- 使用 `capturedAt` 而不是消息到达时间，避免网络延迟改变告警语义。
- 使用 `eventId` 去重，避免 Kafka 重投或客户端重试重复计数。
- 使用 `ruleId + cameraId` 隔离窗口，避免不同摄像头相互污染。
- 使用冷却时间抑制同一持续事件反复生成告警。
- 将内存实现作为领域规则原型，下一阶段再替换成 Redis 原子窗口。

## 总体架构

![MineGuard 总体架构](docs/assets/logical_architecture.png)

| 层次 | 负责内容 | 不负责内容 |
|---|---|---|
| 视觉推理 | 拉流、抽帧、YOLO 推理、同帧画框、发布检测事件 | 不直接认定事故，不直接创建工单 |
| Java 安全核心 | 幂等、规则、告警、状态机、权限、事务和审计 | 不让大模型绕过服务修改数据库 |
| RAG | 检索规程原文、返回证据片段和版本 | 不替代规则引擎做确定性判断 |
| Agent | 基于事实和证据生成结构化研判与工具调用计划 | 不执行任意 SQL，不绕过审批 |
| 人工审批 | 确认高风险动作、修正误报、承担最终业务判断 | 不需要手工处理每一帧预测 |
| 数据治理 | 回收困难样本、审核、重训、独立测试、模型登记 | 不与在线监控服务强耦合 |

## 事件契约为什么重要

模型服务和 Java 后端不通过随意拼接的 JSON 对接，而是使用版本化契约。

| 字段 | 作用 |
|---|---|
| eventId | 入站幂等键，防止重复消费 |
| schemaVersion | 支持以后兼容升级 |
| traceId | 串联推理、告警、Agent、工单和审计日志 |
| cameraId | 区分数据来源，也是 Kafka 分区键候选 |
| frameId | 对齐原始帧和标注帧 |
| capturedAt | 事件时间，是时序规则计算依据 |
| inferredAt | 计算端完成时间，可用于分析推理延迟 |
| modelVersion | 支持模型追责、灰度和回滚 |
| sourceObjectKey | 指向证据文件，而不是把大文件放进消息 |

机器可读定义位于 [detection-frame-event-v1.schema.json](contracts/detection-frame-event-v1.schema.json)。

## 数据库与一致性

- `detection_events` 通过 `event_id` 唯一索引完成入站幂等。
- `alerts` 保存规则、摄像头、类别、风险等级、时间和业务状态。
- `outbox_events` 与业务修改同事务落库，再异步发布外部事件。
- `audit_logs` 记录操作者、动作、对象、时间、traceId 和关键细节。

项目只保留一套明确的 Outbox，不同时启用 Spring Modulith JPA 事件仓库，避免两套可靠消息机制职责重叠。

## 构建与部署

```powershell
Set-Location -LiteralPath 'E:\project11\mine-safety-agent-platform'
mvn clean verify
powershell -ExecutionPolicy Bypass -File .\deploy\install-offline-to-vm.ps1
Invoke-RestMethod http://192.168.1.110:18080/actuator/health
```

部署脚本会创建 MineGuard 独立数据库和账号、读取现有 Redis 认证但不打印密码、写入权限为 `600` 的环境文件、启用 linger，并让服务在 SSH 断开后继续运行。

## 面试讲解顺序

1. 先讲问题：模型框不是业务告警，单帧预测存在抖动和延迟。
2. 再讲架构：Python 感知、Kafka 解耦、Java 确定性业务、RAG 证据、Agent 规划、人类审批。
3. 展示事件协议：重点解释幂等键、事件时间、模型版本和 traceId。
4. 展示时序规则测试：解释 20 秒 3 次、过期淘汰、重复事件和摄像头隔离。
5. 展示数据库：解释唯一索引、状态机、Outbox 和审计如何共同保证可靠性。
6. 运行测试和健康检查，用可复现结果代替口头描述。
7. 最后展示路线图，主动区分已实现、开发中和规划能力。

## 安全边界

- 仓库不提交 RTSP 密码、数据库密码、模型权重和私有数据集。
- 当前项目是工程作品与研究原型，不是经过安全认证的生产系统。
- 高风险处置动作必须经过确定性策略检查和人工确认。
