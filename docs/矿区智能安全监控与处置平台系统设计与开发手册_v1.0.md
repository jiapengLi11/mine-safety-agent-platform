## 1 文档目的

本文档定义矿区智能安全监控与处置平台第一版的产品边界、技术架构、领域模型、数据契约、核心流程、Agent 安全机制、测试方案和开发顺序。它既是后续开发的设计基线，也是项目复盘、团队协作和技术面试讲解的依据。

平台不是让大模型直接监控视频或任意操作业务系统，而是采用分层职责：视觉模型负责感知，规则引擎负责确定性判断，RAG 提供可追溯的规程证据，Agent 生成结构化研判和处置计划，Java 业务服务负责权限、事务、状态迁移与工具执行，高风险动作必须由人确认。

## 2 当前基础与建设结论

项目已有两项经过真实运行验证的基础能力。

第一，已经建立六分类目标检测的数据治理闭环。六个单类别 Teacher 对 29,071 张图像完成 174,426 次模型图像推理，形成 99,696 条预测证据和 30,183 条人工审核任务。流水线使用单模型串行加载、FP16、流式读取、动态 Batch、OOM 自动降级、增量落盘和断点续跑，保持源标签只读。

第二，已经开发 Spring Boot 4、Vue 3 和 MySQL 多人审核平台，具备 JWT 与 RBAC、项目成员隔离、图片级悲观锁原子领图、租约心跳、乐观版本控制、Flyway 数据迁移和审计日志，并在校园网环境完成多账号协作审核。

## 3 产品定位

产品名称为 MineGuard Agent 矿区智能安全监控与处置平台。

目标用户包括监控值班员、安全员、班组负责人、系统管理员、模型管理员和审计人员。

平台解决五类问题。

1. 将摄像头和录像中的视觉检测结果转换为可追踪的业务事件。
2. 使用时序规则过滤单帧抖动和偶发误检，形成稳定告警。
3. 为告警检索适用的安全规程和历史处置依据。
4. 使用受控 Agent 生成风险研判、处置建议和工单草稿。
5. 将误报、漏报和困难样本送回补标平台，持续迭代数据集和模型。

## 4 第一版范围

### 4.1 第一版必须实现

- 使用本地视频、摄像头或 RTSP 地址产生检测事件。
- 接收并持久化统一格式的检测事件。
- 支持按摄像头、类别、置信度、区域和时间窗配置告警规则。
- 支持二十秒内三次吸烟等多帧聚合策略。
- 支持告警去重、合并、抑制、确认、误报和关闭。
- 支持工单创建、领取、处理、复核和完成。
- 支持安全规程入库、混合检索、重排和原文引用。
- 支持 Agent 研判、工具调用、人工审批和全过程审计。
- 支持将告警反馈转换为补标候选。
- 支持 Docker Compose 启动开发环境和固定录像一键演示。

### 4.2 第一版不做

- 不追求未经验证的真实二十路摄像头生产承载能力。
- 不让大模型直接连接数据库或执行任意 SQL。
- 不允许 Agent 绕过业务服务直接改变告警和工单状态。
- 不把一次模型预测直接视为违规事实。
- 不在第一版拆分大量微服务或引入 Kubernetes。
- 不声称替代安全员完成最终责任认定。

## 6 架构原则

### 6.1 确定性逻辑优先

检测阈值、时间窗、告警抑制、权限、状态迁移和工具执行必须由确定性代码完成。大模型只负责需要语言理解和知识推理的环节。

### 6.2 Agent 是规划者而不是数据库操作者

模型可以提出调用工具的请求，但工具是否允许执行、使用什么参数以及是否需要人工批准由 Java 策略层决定。工具只能调用领域服务，不向模型提供数据库连接、文件系统或任意网络访问。

### 6.3 在线链路与训练链路隔离

在线系统只加载经过登记和审核的模型版本。补标、训练、评测和模型发布在离线流水线完成，通过模型注册记录进入在线系统。

### 6.4 所有关键操作可追溯

检测事件、规则版本、模型版本、检索证据、Prompt 版本、Agent 输出、工具参数、审批人和状态变化必须可关联、可查询、可回放。

### 6.5 先模块化单体后服务化

第一版使用 Spring Modulith 管理模块边界和领域事件。只有当推理、知识检索或告警处理出现独立扩缩容需求时才拆分服务。

### 8.2 数据原则

- 原始检测载荷可保存为 JSON，但用于查询和规则计算的字段必须结构化。
- RTSP 密码、模型密钥和大模型密钥不存明文，表中只存密钥引用。
- 图片和视频不写入 MySQL BLOB，统一存入 MinIO，数据库保存对象键和校验值。
- 状态型聚合根使用 version 字段进行乐观锁控制。
- 所有业务表统一使用 UTC 时间，前端按用户时区显示。

## 10 视频与推理服务设计

### 10.1 职责

推理服务负责读取视频、按策略抽帧、图像预处理、模型推理、同帧绘制、结果发布和运行指标，不负责告警判断和工单业务。

### 10.2 抽帧与背压

- 每路视频维护有限长度帧队列，队列满时优先丢弃旧帧而不是无限堆积。
- 推理只消费最新可用帧，避免处理已经过期的历史画面。
- 每帧带 frameId、capturedAt、inferredAt 和 publishedAt。
- 多路视频使用轮询或公平调度，防止单路高帧率占满 GPU。
- 部署输入尺寸以现场约束为准，第一版同时记录 640 和 832 的配置差异。

### 10.3 前端画框原则

推荐后端在被检测的同一帧上绘制框并推送标注流。若前端绘制，则必须使用 frameId 精确对齐并维护有限帧缓存。前端不得把已经画框的截图再次作为模型输入，避免框线、标签和遮挡污染下一次检测。

## 11 时序告警规则引擎

### 11.1 规则配置

```json
{
  "ruleType": "WINDOW_HIT_COUNT",
  "className": "smoking",
  "minimumConfidence": 0.65,
  "windowSeconds": 20,
  "minimumHits": 3,
  "cooldownSeconds": 60,
  "cameraIds": ["CAM-001"],
  "region": null,
  "enabled": true
}
```

### 11.2 执行流程

1. detection 模块完成事件格式和幂等校验。
2. rule 模块过滤类别、置信度、摄像头、模型版本和区域。
3. 将命中时间写入 Redis Sorted Set，键为 ruleId 与 cameraId。
4. 删除时间窗之前的成员并统计剩余数量。
5. 达到 minimumHits 后检查 cooldown 键。
6. 未处于抑制期时创建 Alert，并关联触发它的全部证据帧。
7. 在同一数据库事务写入 Alert 和 OutboxEvent。
8. Outbox 发布器异步发送 AlertCreatedEvent。

Redis 只是窗口计算介质，告警事实以 MySQL 为准。Redis 不可用时，系统进入降级模式，将事件暂存或使用数据库低吞吐计算，不允许悄悄跳过告警。

### 11.3 支持的规则类型

| 类型 | 示例 |
|---|---|
| SINGLE_HIT | 高置信度车辆进入禁区立即告警 |
| WINDOW_HIT_COUNT | 二十秒内三次吸烟 |
| CONTINUOUS_DURATION | 人员在危险区域持续停留十秒 |
| CLASS_COEXISTENCE | 人与拖拉机在危险距离内同时出现 |
| CLASS_ABSENCE | 检测到 person 但一定区域未检测到 helmet |
| SCHEDULED_RULE | 夜间指定区域出现人员 |

## 12 状态机

### 12.1 告警状态

```text
CANDIDATE -> CONFIRMED -> HANDLING -> CLOSED
    |            |            |
    +----------> FALSE_POSITIVE
    +----------> SUPPRESSED
```

### 12.2 工单状态

```text
CREATED -> ACCEPTED -> PROCESSING -> WAITING_REVIEW -> COMPLETED
   |           |            |              |
   +---------> CANCELLED <---+-------------> REJECTED
```

### 12.3 Agent 状态

```text
CREATED -> RETRIEVING -> PLANNING -> POLICY_CHECK
                                      |       |
                                      |       +-> REJECTED
                                      v
                               WAITING_APPROVAL
                                      |
                                      v
                                  EXECUTING
                                  |       |
                                  v       v
                              SUCCEEDED  FAILED
```

状态迁移由聚合根方法完成，不允许 Controller 直接修改状态字段。每次迁移检查当前状态、操作权限、版本号和必要字段，并写入不可变动作记录。

## 13 RAG 知识库设计

### 13.1 文档处理

支持 PDF、Word、Markdown 和纯文本。入库流程为文件校验、病毒扫描、内容解析、章节识别、条款切片、元数据补充、Embedding、检索索引和人工抽查。

切片优先遵循标题、章节和条款边界。每个 Chunk 保存 documentId、documentVersion、clauseNo、pageNo、effectiveDate、region、equipmentType、riskType 和 checksum。

### 13.2 检索流程

```text
用户问题或告警事实
-> 查询意图与风险分类
-> 权限和适用范围过滤
-> BM25 关键词召回
-> 向量语义召回
-> 合并去重
-> Reranker 重排
-> 选择前五条证据
-> 生成结构化回答
-> 引用覆盖校验
-> 返回答案或拒答
```

### 13.3 证据控制

- 每条结论必须关联 chunkId 和原文位置。
- 高风险答案必须至少有一条当前有效规程证据。
- 证据冲突时返回冲突说明，不由模型自行选择法规版本。
- 未检索到可靠证据时输出 NEED_HUMAN，不允许编造条款。
- 文档中的指令文本视为不可信数据，不能覆盖系统策略或工具权限。

### 13.4 RAG 评测

建立至少五十道固定测试题，覆盖直接事实、跨条款综合、版本冲突、无答案、权限隔离和恶意提示注入。记录 Recall at 5、MRR、引用精确率、引用覆盖率、答案忠实度和正确拒答率。

## 14 Agent 设计

### 14.1 Agent 输入

Agent 只接收已形成的 Alert，不接收连续原始视频。输入由 alert facts、evidence summary、device context、applicable rules、retrieved clauses 和 operator request 组成。

### 14.2 Agent 输出

```json
{
  "riskLevel": "HIGH",
  "violationType": "SMOKING",
  "assessment": "检测到人员在作业区域持续吸烟",
  "evidenceIds": ["EVIDENCE-101", "EVIDENCE-102"],
  "citations": [
    {"chunkId": "CHUNK-88", "clauseNo": "第某条", "pageNo": 12}

  "recommendedActions": ["通知现场安全员", "形成处置工单"],

  "requiresHumanApproval": true,
```

| upgradeAlert | 高风险写 | 否 | 必须人工批准和角色校验 |

### 14.4 两阶段执行

第一阶段由模型生成 ActionPlan，策略层完成 Schema 校验、证据检查、工具白名单、权限、风险等级和参数范围检查。第二阶段由 ActionExecutor 执行已批准动作。高风险动作先形成 PendingAction，审批通过后才调用领域服务。

### 14.5 Agent 运行限制

- 单次最多八个步骤。
- 单次最多五次工具调用。
- 设置总超时、单工具超时和 Token 上限。
- 禁止递归调用同一写工具。
- 工具调用使用 idempotencyKey。
- 模型输出必须通过 JSON Schema 校验。
- 连续格式失败时终止并转人工。
- 大模型不可用时保留普通告警和人工处置能力。

## 15 权限与安全设计

| 角色 | 权限摘要 |
|---|---|
| ADMIN | 用户、角色、设备、系统配置 |
| OPERATOR | 查看监控、确认告警、填写备注 |
| SAFETY_OFFICER | 研判告警、审批 Agent 动作、创建和关闭工单 |
| SUPERVISOR | 告警升级、复核工单、统计分析 |
| MODEL_MANAGER | 模型登记、灰度发布、反馈样本管理 |
| AUDITOR | 只读查看事件、Agent 步骤和审计记录 |

安全措施包括 JWT 短期访问令牌、刷新令牌轮换、BCrypt 或 Argon2 密码哈希、接口限流、参数校验、对象级权限、密钥外置、敏感日志脱敏和文件类型校验。

Prompt、知识文档和用户输入均按不可信数据处理。Agent 的系统策略、允许工具和审批规则由服务端固定，不能被文档内容或用户消息覆盖。

## 16 可靠消息与一致性

### 16.1 入站幂等

Kafka 消费者在业务事务内插入 eventId 唯一记录。若唯一键冲突则认为消息已经处理，不重复生成告警。

### 16.2 Transactional Outbox

创建告警、工单或反馈时，在同一 MySQL 事务写业务表和 outbox_events。后台发布器批量锁定待发送事件，发布到 Kafka 后更新状态；失败时指数退避，超过次数进入人工处理队列。

### 16.3 顺序和乱序

检测 Topic 使用 cameraId 作为分区键，保证单摄像头内基本有序。消费者仍以 capturedAt 处理有限乱序，超过允许延迟的事件记录为 LATE，不回写已经关闭的窗口。

### 16.4 降级策略

| 故障 | 降级行为 |
|---|---|
| LLM 不可用 | 保留规则告警，Agent 状态转 WAITING_RETRY |
| Elasticsearch 不可用 | 禁止高风险自动建议，转人工查规程 |
| Redis 不可用 | 暂存事件或使用数据库低吞吐窗口计算 |
| Kafka 短时不可用 | 推理端有限磁盘缓冲，恢复后重发 |
| MinIO 不可用 | 保留事件元数据，证据状态标记缺失并告警 |

## 19 可观测性

统一链路标识为 frameId、eventId、alertId、agentRunId 和 workOrderId。OpenTelemetry Trace 应覆盖推理事件发布、Kafka 消费、规则计算、RAG 检索、模型调用、工具调用和工单写入。

重点指标包括 detection_event_total、detection_lag_ms、rule_evaluation_ms、alert_created_total、duplicate_event_total、agent_run_duration_ms、agent_tool_call_total、rag_retrieval_duration_ms、work_order_completion_time 和 outbox_pending_total。

日志使用结构化 JSON，禁止打印 RTSP 密码、大模型密钥、完整 JWT 和未经脱敏的个人信息。

## 21 设计目标与验收指标

以下均为待验证目标，不是当前已取得的性能声明。

| 领域 | 第一版目标 |
|---|---|
| 功能闭环 | 固定视频能够完成检测、三次命中、告警、RAG、审批、工单和反馈 |
| 幂等性 | 同一检测事件重复投递十次只产生一个业务结果 |
| 状态安全 | 自动测试中非法状态迁移成功次数为零 |
| Agent 安全 | 未批准高风险动作实际执行次数为零 |
| RAG | Recall at 5 不低于 85%，引用精确率不低于 95% |
| 稳定性 | 二十路录像模拟连续运行两小时，无无限队列和内存持续增长 |
| 事件延迟 | 不含模型推理的告警处理 P95 小于 500 毫秒 |
| 可恢复性 | Java 服务重启后未完成 Outbox 和 Agent 任务可恢复 |
| 可观测性 | 任一工单可以追溯到原始检测事件、模型和规程证据 |

## 29 设计基线结论

第一版以可运行、可复现、可解释为优先级。在线主链路必须在没有大模型时仍能生成告警和完成人工工单；Agent 的价值是结合证据提高研判和处置效率，而不是代替确定性业务系统。

当固定视频能够稳定完成检测、时间窗告警、规程检索、Agent 计划、人工审批、工单闭环和样本反馈时，平台才具备完整的第一版交付条件。后续所有技术选型和新增需求均应围绕这一闭环评估，避免偏离项目目标。
